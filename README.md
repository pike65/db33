# ✳️ Quick Start

Requirements: **Docker Desktop** (must be running). Nothing else is needed.

1. Unzip the archive and open the folder in VS Code.
2. Open a terminal in VS Code (Terminal > New Terminal).
3. Run:

   ```bash
   docker compose up --build -d
   ```

4. Wait about 10 seconds, then open the Swagger UI:

   **http://localhost:8000/docs**

The database starts **empty**: the tables exist, but there is no data. Follow the next section: first create the research and expertise areas, then the sample data.

Deployed version: see `links.txt`.

# ❇️ Typical Workflow

Run these after the project is up. The order matters.

1. **Create the research and expertise areas**

   Open http://localhost:8000/docs, find `POST /populate-areas`, click **Try it out**, then **Execute**. It fills both area tables and can be run more than once without duplicates. The seed script needs these areas.

2. **Fill the database with sample data**

   ```bash
   docker compose exec app python -m app.database.seed
   ```

   If the areas are missing, the script stops and tells you to do step 1. Refresh `/docs` and try the endpoints (for example `GET /users`).

3. **Run the Part 2 queries**

   ```bash
   docker compose exec app python -m part2.run_part2
   ```

   Prints every task with its SQL and results. It needs the areas and the sample data from steps 1 and 2. The script restores the sample data after every update or delete. It also deletes all users, papers and conferences first, so run it only when you do not need your own changes.

   The output is also saved to `/app/part2_output.txt` inside the container. To copy it to the project folder:

   ```bash
   docker compose cp app:/app/part2_output.txt ./part2_output.txt
   ```

   A copy generated by the authors is included in the archive as `part2_output.txt`.

4. **Restore the original sample data**

   ```bash
   docker compose exec app python -m app.database.seed --reset
   ```

   Wipes the whole database and restores the areas and the sample data. No need to repeat step 1.

5. **Experiment** in Swagger or psql. Repeat step 4 at any time to start again from the original data.

## Structure

1. The web app uses a modular structure: each entity's endpoints, service logic and schemas are isolated in `app/modules/<domain_name>/`.
2. Shared resources (settings, exceptions) are in `app/core/`.
3. Tables (models), the database connection and the seed script are in `app/database/`.

# 🗂️ Database Restoration

Two equivalent ways to get the original dataset.

1. **Seed script (recommended):** `docker compose exec app python -m app.database.seed --reset` drops everything, recreates the tables, restores the research and expertise areas and inserts the original data.
2. **SQL dump:** `dump.sql` is a plain `pg_dump` export with the schema, the areas, the sample data and the view `accepted_paper_schedule`. It must be loaded into a database without tables, because the app creates tables on startup:

   ```bash
   docker compose down -v
   docker compose up -d db
   docker exec -i db3_container psql -U neo -d db3_db < dump.sql
   docker compose up -d
   ```

# 🧬 Schema and Keys

Table and column names are in `app/database/models.py`.

| Table | Primary key | Foreign keys (delete action) |
|---|---|---|
| `users` | user_id | none |
| `authors` | author_id | author_id -> users (CASCADE) |
| `reviewers` | reviewer_id | reviewer_id -> users (CASCADE) |
| `research_areas` | research_area_id | none (label is unique) |
| `expertise_areas` | expertise_area_id | none (label is unique) |
| `author_research_areas` | (author_id, research_area_id) | -> authors, -> research_areas (CASCADE) |
| `reviewer_expertise_areas` | (reviewer_id, expertise_area_id) | -> reviewers, -> expertise_areas (CASCADE) |
| `conferences` | conference_id | none |
| `hosts` | (conference_id, host_name) | -> conferences (CASCADE) |
| `maintained_conferences` (reviewer pool) | (reviewer_id, conference_id) | -> reviewers, -> conferences (CASCADE) |
| `tracks` | track_id | conference_id -> conferences, research_area_id -> research_areas, reviewer_id (coordinator) -> reviewers (all CASCADE) |
| `sessions` | session_id | conference_id -> conferences, reviewer_id (chair) -> reviewers (both CASCADE) |
| `papers` | paper_id | track_id -> tracks (CASCADE), session_id -> sessions (SET NULL, nullable) |
| `keywords` | (paper_id, keyword) | -> papers (CASCADE) |
| `author_papers` | (author_id, paper_id) | -> authors, -> papers (CASCADE) |
| `paper_versions` | (paper_id, version_number) | -> papers (CASCADE) |
| `reviews` | review_id | paper_id -> papers, reviewer_id -> reviewers (both CASCADE) |

Multivalued attributes (research areas, expertise, keywords, hosts) are stored in separate tables, never as comma-separated text.

Deleting a conference removes only its own records (hosts, reviewer pool, tracks, sessions and their papers). It never deletes users or reviewers.

Deleting a user or reviewer profile also removes the tracks they coordinate, the sessions they chair and their reviews (CASCADE). The application refuses to delete the last remaining profile (author or reviewer) of a user.

## Database constraints

| Required constraint | Implementation |
|---|---|
| Unique user email | `users.email` UNIQUE |
| Unique author position per paper | `author_papers` UNIQUE (paper_id, author_order) |
| One review per reviewer and paper | `reviews` UNIQUE (reviewer_id, paper_id) |
| Status is submitted, under review, accepted, rejected or withdrawn | CHECK `check_paper_status` |
| Score is an integer from 1 to 5 | CHECK `check_overall_score` |
| Recommendation is accept or reject | CHECK `check_recommendation` |
| Author position is positive | CHECK `check_author_order_positive` |
| Version number is positive | CHECK `check_version_number_positive` |
| Reviewing experience is not negative | CHECK `check_if_xp_years_is_nonnegative` |
| Conference end date is not earlier than start date | CHECK `check_start_not_after_end` |
| Session end time is later than start time | CHECK `check_start_earlier_than_end` |
| Versions are deleted with their paper | `paper_versions.paper_id` ON DELETE CASCADE |
| A paper has at most one session | `papers.session_id` (single nullable column) |
| Only completed reviews are stored | review fields are NOT NULL |

## Differences from the reference schema (Appendix A)

1. Table and column names differ (for example `years_of_experience`, `author_order`, `version_number`, `upload_datetime`, `room`). The meaning is the same.
2. `users.phone_number` is NOT NULL and UNIQUE.
3. `reviews.confidential_comments` is NOT NULL (optional in Appendix A).
4. Session start and end are stored as timestamps with time zone, together with `session_date`.
5. The track coordinator and the session chair are stored in a column named `reviewer_id`.

# ✅ Required Application Checks

Both checks are enforced in the service layer. A rejected request returns an error message and changes nothing.

1. **No self-reviews.** A review is rejected if its reviewer is an author of the paper. Checked when a review is created, when a review is updated (reviewer or paper changed), and when the authors of a paper are changed (a paper cannot get an author who has already reviewed it).
2. **Valid session assignment.** A paper in a session must be accepted, and its track and the session must belong to the same conference. Checked when a paper is created or updated (session, status or track changed). An invalid change is **rejected**; the assignment is not removed silently. Moving a session or a track to another conference is rejected while it would break an assigned paper.

To try them in Swagger (after seeding):

- **Self-review:** `POST` a review on the paper "Neural Query Cardinality Estimation" with Arman Armanov as reviewer. He is an author of that paper, so the request is rejected.
- **Invalid session, wrong status:** update the paper "Graph Embeddings for Clinical Triage" (status submitted) with the id of the session "Keynote & Accepted Papers". The request is rejected.
- **Invalid session, wrong conference:** create a session in the Berlin conference, then assign the accepted paper "Low-Latency Transformers on Edge Nodes" (Astana) to it. The request is rejected.
- **Status change:** change the status of "Neural Query Cardinality Estimation" (it has a session) to rejected. The request is rejected.

# 📏 Other Business Rules

All rules hold in the sample data. The application enforces only what the last column says.

| Rule | Enforced? |
|---|---|
| Every user is an author, a reviewer or both | Partly: the last remaining profile of a user cannot be deleted. Not checked when creating a user (holds in sample data). |
| A paper is created together with a version | Yes (the version is part of the create request) |
| Exactly one corresponding author per paper | No (holds in sample data) |
| Track coordinators and session chairs belong to the conference's reviewer pool | No (holds in sample data) |

# 📝 Design Assumptions

1. No authentication and no real file upload. Each paper version stores only a file path (for example `/files/p1_v1.pdf`).
2. The current version of a paper is the one with the highest version number. Gaps are allowed.
3. A user can be an author, a reviewer or both (one row in `users`, plus rows in `authors` and/or `reviewers`).
4. Research and expertise areas are created through `POST /populate-areas` and are read-only afterwards. Conferences (with hosts, reviewer pool and tracks) can be created, read, updated and deleted through the API.
5. Full CRUD is available for users (with author and reviewer profiles), papers (with authors, keywords and versions), reviews and sessions.
6. Dates and times are stored in UTC.
